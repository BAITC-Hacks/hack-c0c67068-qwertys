# План команды HackAlem AI с 13 40 до 18 00

> Исходный подробный план. После публикации стартовой ветки актуальные сроки, назначения и Git-протокол берутся из `coordination/START_HERE.md`, `SCHEDULE.md` и `ROLES.md`. Отдельные исследования уже обновлены в `coordination/RESEARCH.md`. При расхождении эти новые документы имеют приоритет.

Старт с нуля. Два участника, два ноутбука, четыре рабочих агента Codex и один Claude. На первом ноутбуке работают три Codex, на втором — Codex и Claude. Этот документ задаёт порядок разработки, ответственность и условия приёмки. Реализация кейса, обучение моделей, обращения к платным API и запуск облачных машин в рамках подготовки плана не выполнялись.

Решение по времени: обязательная версия готова к 17:00; с 17:00 до 17:40 допустимы улучшения только при выполненных обязательных требованиях; 17:40–18:00 — защищённый технический резерв. Получается 200 минут обязательной работы + 40 минут условных улучшений + 20 минут резерва. При отставании последние 40 минут превращаются в резерв: 200 + 60 минут. Четыре часа разработки и ещё час резерва до 18:00 не помещаются: для этого нужен старт в 13:00.

Расписание рассчитано от указанного командой времени 13:40. Если фактический старт позже, сначала сокращается блок улучшений, затем оформление; время финальной отправки не сдвигается.

## Критический путь и работа без ожидания

Критический путь: доказательство пригодности архива → согласование времени и данных → один корректный прогноз → связанный агентный цикл → полный февраль → повторный запуск → сдача.

C1 имеет наивысший приоритет по блокирующим вопросам. Пока архив проверяется, C2 делает аудит и baseline на доступной истории, C3 работает по фиксированной схеме, C4 — по помеченным примерам, Claude — по критериям приёмки. Участник A объединяет изменения небольшими порциями, начиная с контрактов; не откладывает первое объединение до конца разработки.

На каждой границе этапа — короткая синхронизация людей до двух минут, включённая во время этапа. Формат: что запущено и доказано; что мешает; кто и к какому времени устраняет. Если блокер не решается за пять минут, агент сообщает его человеку и продолжает независимую часть работы. Полный перепроектирование через длинный общий чат не допускается.

Это выбор для четырёхчасового окна, а не рейтинг всех существующих технологий. Критерии: корректность временного эксперимента, скорость получения измеримого результата, удобство интеграции и воспроизводимость на втором ноутбуке.

| Слой | Основной выбор | Ограничение времени или сложности |

Для CatBoost доступны официальные примеры регрессии: [примеры Python](https://catboost.ai/docs/en/concepts/python-usages-examples). LangGraph допустим, если C3 уже уверенно работает с ним и успевает к тем же контрольным точкам. Обязательной зависимости от большого агентного фреймворка нет. Kubernetes, микросервисы, векторная БД, RAG, дообучение LLM и тяжёлые временные foundation models не входят в обязательную версию.

## Проверка погодного источника

Кандидат для первой проверки — Open-Meteo Single Runs. Документация позволяет выбирать отдельный запуск, но для большинства моделей архив начинается только 2 апреля 2026 года. Для ECMWF IFS заявлен более ранний период и присутствует формулировка hindcasts. Следовательно, одного совпадения даты недостаточно: необходимо подтвердить, что выбранные данные действительно представляли прогноз, доступный тогда, а не последующий пересчёт. Начало запуска модели также не равно моменту публикации результата. [Single Runs API](https://open-meteo.com/en/docs/single-runs-api).

Второй кандидат — Previous Runs API, где данные выровнены по срокам упреждения. Это не готовая гарантия доступности всех значений в едином выбранном времени выпуска. Перед использованием C1 обязан доказать это для каждого срока и переменной. [Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api).

К 14:10 C1 предъявляет: координаты, имя модели/провайдера, покрытие февраля и исторического периода проверки, пример ответа, время запуска и обоснование времени доступности. Реальные запросы к архиву при подготовке этого плана не выполнялись; проверка эндпоинта входит в работу команды.

Если пригодность не подтверждена, A сразу привлекает ментора: нужен указанный организатором допустимый архив или подтверждённый альтернативный оперативный источник. К 14:25 принимается решение о конкретном источнике. Реанализ и фактическая погода не считаются выполнением этого пункта. Если источник получить не удастся, это остаётся открытым обязательным требованием и должно быть честно отражено в сдаче.

| Строка прогноза | Идентификатор запуска, турбина, момент прогнозирования, целевой час, упреждение, прогноз, единица и отметка резервного режима |
| Результат проверки | Исторический период, способ разделения данных, baseline, MAE/RMSE по турбинам и горизонтам, покрытие, длительность |
| Журнал агента | Инструмент, безопасное описание входа, результат/ошибка, решение о следующем шаге и повторе; секреты не записываются |

Основной ключ прогнозов включает и время выпуска, и целевой час: при горизонте 48 часов один целевой час может иметь несколько прогнозов. Правило выбора строки для итоговой оценки фиксируется до сравнения моделей. Февраль содержит 672 часа; полное уникальное покрытие двух турбин составляет 1344 пары «турбина–целевой час». Журнал всех выпусков с перекрывающимися горизонтами содержит больше строк.

Полные 48-часовые горизонты сохраняются в журнале; для тестового файла отдельно отбираются целевые часы февраля по требованиям организаторов. Границы суток и часовой пояс должны быть согласованы до проверки количества строк.

## Приёмка ML и защита от будущих данных

1. Выделить исторический период для настройки и отдельный поздний период для итоговой проверки до февраля. Например, декабрь для настройки и январь для проверки при наличии нужного погодного архива. Разделение закрепить до экспериментов.
2. Делить по времени одновременно для обеих турбин. Случайное перемешивание соседних измерений не использовать как доказательство качества прогноза.
3. Все преобразования, отбор признаков и настройку выполнять на доступной на тот момент истории. Не использовать будущие наблюдения или двустороннее заполнение пропусков через границу прогноза.
4. Оценивать сквозной прогноз с архивной прогнозной погодой. Если дополнительно проверяется зависимость мощности от измеренного ветра, явно назвать это отдельной диагностикой, не итоговой точностью 24/48 часов.
5. Сравнить основной кандидат с baseline на одних и тех же целевых часах и при одинаковой доступности входов. Показать MAE и RMSE, покрытие, различия между турбинами и горизонтами. Не назначать выдуманный порог точности заранее.
6. Для февраля не использовать лаги фактической мощности и локальных измерений, которых в выдаче нет. Вариант без этих входов либо явно описанный рекурсивный режим должен работать весь месяц.
7. После выбора подхода разрешено финальное обучение на доступных данных до 31 января. Февральские ответы и фактическую погоду будущего не подмешивать.
8. Метрики за февраль не рассчитывать без истинных значений. В интерфейсе и README разделить историческую проверку и прогноз тестового периода.
9. Не суммировать нормализованные мощности двух турбин в МВт. Агрегацию ВЭС и перевод в энергию делать только при известных коэффициентах и согласованных единицах.

## Что считается настоящим агентным сценарием

Система получает запрос, выбирает и вызывает ограниченный набор инструментов, проверяет доступность и качество входов, запускает численную модель, формирует результат, анализирует предупреждения и пересчитывает результат при обновлённой версии погоды. Все действия видны в журнале.

На демонстрации должен быть реальный вызов инструментов и наблюдаемый переход состояния. Нарисованный журнал или заранее сгенерированное объяснение не подтверждает Agentic AI. Числа прогноза и метрики вычисляет модель/код, а не свободный ответ LLM.

При недоступности LLM допустим воспроизводимый расчёт через Python и просмотр сохранённого журнала ранее выполненного агентного запуска. Интерфейс честно помечает резервный режим; это не выдаётся за новый успешный живой вызов агента.
