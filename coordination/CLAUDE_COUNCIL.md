## Жёсткий таймбокс

Совет занимает максимум **20 минут от фактического старта и заканчивается не позднее 14:35**. Доступное время = min(20 минут, 14:35 − старт). Никаких фоновых раундов после отсечения.

| Интервал от старта | Действие |
|---|---|
| 0–2 минуты | Claude публикует старт, ограничения, форму ответа; B доставляет задания существующим C2/C4 |
| 2–7 минут | Независимая генерация: Claude 12–18 идей, C2 и C4 по 9–16; суммарно 30–50 сырых идей, включая пересечения |
| 7–10 минут | Claude объединяет похожие идеи, сохраняет авторство, отсеивает запрещённые; публикует shortlist 5–8 кандидатов |
| 10–14 минут | Каждый из трёх исполнителей независимо оценивает один и тот же shortlist, не читая чужие бюллетени |
| 14–17 минут | Claude проверяет числа, противоречия и veto; рассчитывает результат и выделяет риски |
| 17–20 минут | A ратифицирует одну P0 линию и не более двух P1; Claude публикует решение и возвращается к QA |

Если осталось менее 10 минут, немедленно сокращать ширину генерации и явно отметить неполноту. Если старт после 14:35, масштабный совет отменён: короткая проверка рисков максимум 5 минут без изменения принятой P0 линии. Нельзя имитировать 30–50 идей, отсутствующие ответы, голоса или консенсус ради численного плана. При менее трёх ответивших результат называется **предварительной рекомендацией**, а не независимым голосованием. Разработка идёт по принятому плану до ратификации A; молчание A не является одобрением.

## Отсечения до голосования

Идея не проходит в P0/P1 при любом из условий:

1. Требует будущих наблюдений или опубликованного позднее прогноза; использует тест для выбора параметров; выдаёт реанализ за доступный тогда прогноз.
2. Требует февральского факта, которого нет, либо непроверенного погодного архива на критическом пути. Исследование неизвестного источника может остаться задачей C1, но не превращается в доказанное основание решения.
3. Нет исполнителя, реалистичной оценки времени, зависимости не доступны или реализация с интеграцией и проверкой угрожает сдаче в 17:00.
4. Нужны неизвестные/недоступные платные ресурсы; API/GPU — самоцель; отсутствует рабочий CPU/проверенный резервный путь там, где это необходимо.
5. Обещает физические единицы, точность, экономию или функции без данных и проверки.

Каждое veto сопровождается свидетельством или точно обозначенным неизвестным. Спорные обязательные факты передаются C1/A; простое большинство не отменяет требования кейса.

## Формула и решение

Каждый кандидат оценивается от 0 до 5 по семи шкалам: K — вклад в обязательные критерии; F — выполнимость до 17:00 с проверкой; D — доказательность и доступность данных; I — простота интеграции; V — польза пользователю/демонстрации; R — экономность ресурсов; N — оригинальность.

`S = 20 × (0.25K + 0.25F + 0.15D + 0.15I + 0.10V + 0.05R + 0.05N)`.

Для кандидата агрегировать **медиану итоговых S независимых исполнителей**, показать также min/max и все исходные оценки. Confidence указывать отдельно как low/medium/high со ссылкой на evidence, не скрывать его в красивом итоговом числе. При равенстве выигрывает меньшая оценка интеграции+проверки в минутах, затем меньший риск данных. Не усреднять разные дубликаты одной идеи так, чтобы получались дополнительные голоса.

Итог: **одна связная P0 линия**, закрывающая требования целиком; **максимум две независимые P1 идеи**, каждая с собственным владельцем и проверкой, запускаемые только после готовности P0 и разрешения A. По умолчанию реализуется не больше одного улучшения одновременно; вторая P1 — резервный кандидат. Для P1 рекомендованный предел реализации+проверки 20 минут каждая. Более смелые идеи, долгие эксперименты, новые источники, GPU и коммерческие гипотезы — отдельный roadmap, не обещания на сегодня.

## Обмен через Git и точные выходы

Каждый работает в **собственной рабочей копии/worktree**. Канонические ветки из GIT_PROTOCOL: C1 — `agent/c1-data`, C2 — `agent/c2-ml`, C3 — `agent/c3-backend`, C4 — `agent/c4-ui`, CLAUDE — `agent/claude-review`. C3 как координатор пишет в `coord/hackalem-start`. Другие написания веток не создавать. Не переключать ветку в общей используемой другими агентами папке. Не делать force-push, не переписывать историю. Только A или явно назначенный им интегратор переносит коммиты в `coord/hackalem-start`.

Общий `RUN_ID` выбирает Claude: локальная дата/время старта в формате `YYYYMMDDTHHMMSS+0500`. Все перечисленные ниже пути относительны корню репозитория; `<RUN_ID>` заменяется одинаковым фактическим значением.

| Файл | Единственный владелец | Содержание |
|---|---|---|
| `coordination/council/<RUN_ID>/brief.md` | CLAUDE | Старт, срок окончания, состояние квот, источники, неизвестные, участники |
| `coordination/council/<RUN_ID>/ideas/<ROLE>.md` | Соответствующая роль | Собственные идеи до ознакомления с идеями остальных |
| `coordination/council/<RUN_ID>/shortlist.md` | CLAUDE | Единый список 5–8 кандидатов с ID, исходными авторами и отсечениями |
| `coordination/council/<RUN_ID>/votes/<ROLE>.json` | Соответствующая роль | Независимый бюллетень по всем кандидатам |
| `coordination/council/<RUN_ID>/ledger.md` | CLAUDE | Время/commit получения, таблица голосов, dissent, формула, статус рекомендации |
| `coordination/council/<RUN_ID>/decision.md` | CLAUDE | P0, до двух P1, владельцы/файлы/сроки/stop rules, отклонённые альтернативы |
| `coordination/council/<RUN_ID>/roadmap.md` | CLAUDE | Идеи после хакатона и недостающие доказательства |
| `coordination/messages/<TIMESTAMP>-<ROLE>-<UNIQUE>.md` | Автор сообщения | Адресат, тема, commit, файлы, действие/срок, blocker или ACK |

Сообщения append-only: новый уникальный файл на каждое сообщение, старые не редактируются. Коррекция — новое сообщение со ссылкой на прежнее. `ledger.md` изменяет только Claude, добавляя записи; каждый бюллетень изменяет только его автор. Раунд фиксируется commit shortlist: бюллетень ссылается именно на него. До сдачи своего бюллетеня не читать `votes/` других исполнителей. Claude также фиксирует собственный бюллетень до чтения чужих.

Передача: сохранить только свои файлы → commit с ролью/темой → push своей ветки → сообщение с SHA. Получатель делает fetch, читает указанный файл/commit и отвечает ACK новым файлом. Не делать автоматическое слияние всех веток. A ратифицирует отдельным сообщением `...-A-ratify-....md` со ссылкой на SHA `decision.md`, выбранными ID и назначениями; Claude записывает ссылку в ledger. Не считать устное намерение проведённым голосованием или применённым изменением.

Минимальная структура бюллетеня (повторить объект candidate для каждого кандидата):

```json
{
  "role": "C2",
  "independent_executor": true,
  "shortlist_commit": "ACTUAL_SHA",
  "candidates": [{
    "id": "I-01",
    "scores": {"K": 0, "F": 0, "D": 0, "I": 0, "V": 0, "R": 0, "N": 0},
    "evidence": ["path-or-primary-source: exact observation"],
    "confidence": "low",
    "effort_minutes": {"implementation": 0, "integration_and_check": 0},
    "owner": "ROLE_OR_UNASSIGNED",
    "files": ["proposed/path"],
    "dependencies": ["specific available dependency or unresolved prerequisite"],
    "stop_rule": "observable trigger and deadline",
    "veto": null,
    "reason": "short independent rationale"
  }]
}
```

Нули в примере — шаблон, не оценки. Каждую идею также снабдить кратким ожидаемым результатом, проверкой приёмки и планом отката. Назначение владельца в бюллетене является предложением до ратификации A.
