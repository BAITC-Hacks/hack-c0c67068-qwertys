## C1: пригодный обучающий набор

Продолжать уже согласованную с C2 загрузку 119 ежедневных ECMWF-выпусков; не дублировать сетевую работу. Передавать готовые train/validation части первыми, далее январский holdout и февральский replay. Для каждой части manifest: период, источник и точный запрос, run time, предполагаемая доступность и её основание, SHA исходного payload, units, coverage/missing, лицензия/атрибуция, локальный путь, размер. Секреты не включать. В Git — код/manifest и разрешённые небольшие примеры, не исходные SCADA или крупный архив.

Проверить полноту запрошенного периода и явным списком исключённые/недоступные выпуски. Ошибка одной загрузки не должна превращаться в незаметную подмену reanalysis или нулями. Повторять ограниченно, соблюдать лимиты, продолжать с места остановки. Передавать C2 конкретные успешные части и пропуски, не ждать конца всей выгрузки.

Длиннее история полезна только при пригодном происхождении и совпадающих признаках. После первой части согласовать с C2 дополнительный pretest-период для сезонности и устойчивости; сначала оценить доступность, размер и время. Отсутствие длинной архивной истории записать как ограничение, не смешивать наблюдения и оперативные прогнозы под одной меткой.

## C2: качество обучения подтверждается экспериментом

- Заморозить протокол: train/validation/final test по времени целевых часов, без overlap целей между частями. Fit imputer/scaler/feature selection только на train. Доступность лагов и погоды проверяется отдельно для каждого issue_time. При перекрывающихся прогнозах единица подсчёта метрик и веса явно описаны.
- Сравнить минимум простой baseline и основной кандидат на одинаковых строках/признаках доступности. До финального январского test использовать validation; по возможности два последовательных pretest временных fold для проверки устойчивости. Если данных недостаточно, сообщить это и не рисовать уверенные интервалы.
- Ограниченный tuning на validation; зафиксировать диапазоны, trials и stop deadline. Проверить train–validation gap и одну полезную ablation, если это помещается до рабочего результата. Не подбирать по final test. После открытия final test любые изменения обозначать post-test, прежний test больше не считать нетронутым.
- Отчёт: MAE, RMSE, signed bias с определением знака, отдельно turbine1/2 и lead1–24/25–48; sample count, missing/coverage, baseline delta. Для нормированных метрик показать знаменатель, не выдумывать мощность в MW или диапазон[0,1]. Низкую метрику расследовать, а не объявлять утечкой без доказательства.
- Сохранить split/config/seed/версии/source hashes, команду train/predict/evaluate, время, артефакт и ограничения. Финальный кандидат выбирается по общей пригодности; отсутствие доказанного улучшения означает сохранение baseline, не сокрытие результата.
- Февраль без labels — прогноз/replay, не измеренная точность. UTC+6 и run+9h остаются inferred/unconfirmed. Не объявлять историческую доступность доказанной.

## C4 / Codex2: строгая независимая приёмка

Создай `docs/verification/acceptance-matrix.md`: требование → проверка/команда → ожидаемый исход → фактический исход → evidence/commit → PASS/FAIL/BLOCKED/NOT_RUN. Не считать заявление автора доказательством. Не считать 19 транспортных тестов проверкой качества модели или всего продукта. Проверять реальные артефакты после подключения C2; маленькие синтетические negative tests подходят для границ.

Обязательные группы:

1. Данные/время: SHA, units, timezone/provenance labels, temporal split, отсутствие future inputs, сохранение overlap origins, пропуски/NaN/inf/duplicate timestamps и корректное покрытие24/48.
2. Модель: воспроизвести команду и независимо пересчитать метрики из сохранённых predictions/labels; сверить baseline на том же sample, per-turbine/per-lead отчёт и fit transforms только train. При отсутствии доказательства писать BLOCKED/NOT_RUN.
3. Агент: один реальный LLM tool-calling проход при доступе, наблюдаемые вызовы и результат; ограниченные retry/timeout; отказ LLM/погоды, корректно помеченный fallback; новый run_id и сохранение старого при пересчёте. Не записывать имитацию как live.
4. API/UI: обе турбины и24/48, schema/units, not_ready/error/cancel если реализован; неизвестныйrun, неверная дата, незавершённый экспорт. UI показывает те же числа, что CSV и API; не только HTTP200.
5. Воспроизводимость: чистая среда ноутбука2 по README, необходимые версии, путь к данным, env без секретов, import/start/build и один полный расчёт. Кэш/replay явно отличаются от live.
6. UX и производительность: основной сценарий без подсказок разработчика, клавиатура/фокус, читаемые подписи и контраст, пустые/ошибочные состояния, отсутствие бесконечного polling. Измерить фактическую длительность baseline/API первого расчёта, не обещать ненаблюдённые миллисекунды.

BLOCKER для объявления «готово»: утечка целей, выдуманные метрики/единицы/успешные tools, потеря результатов, недоступный основной запуск, раскрытие секретов, неверный экспорт. Неизвестный исторический provenance — явное ограничение соответствия кейсу, не PASS; можно передать работоспособный прототип с раскрытым ограничением, нельзя объявлять требование доказанным. Cosmetic shortcomings — ниже приоритета. Тесты должны проверять поведение/инварианты; бессмысленное увеличение числа тестов не цель.

## Claude: выразительный интерактивный рабочий интерфейс

Усилить уникальность и интерактивность существующего web/, не пересоздавать приложение. Дизайн строится вокруг реального решения диспетчера: выбранная турбина, дата выпуска, горизонт, ход расчёта, результат, сравнение, экспорт. Одна согласованная визуальная система с собственными цветом/типографикой/иерархией; не нужен типовой лендинг с карточками вместо продукта.

Приоритет после текущего работающего экрана:

1. Интерактивный график: общий crosshair/tooltip, включение/выключение турбин, читаемые даты/единицы, доступная таблица тех же данных; масштаб/выделение диапазона, если текущая библиотека позволяет быстро и надёжно.
2. Лента настоящих агентных событий с раскрытием кратких входов/выходов, времени и ошибок без секретов/внутренних рассуждений. Состояния pending/running/error/complete берутся из API. Никакого декоративного «агент думает», выдаваемого за факт.
3. Сравнение двух реально сохранённых runs по общим valid hours: overlay и delta, явно видимые origin/run_id. Пока второго результата нет — объяснимое недоступное действие, не фальшивый график.
4. Контекстный блок доверия: источник, run time, assumption/provenance, coverage, режим live/cached/deterministic. Детали раскрываются по запросу, основные ограничения видны до интерпретации графика.
5. Аккуратные переходы состояния, skeleton на загрузке, понятное восстановление после ошибки, клавиатура, responsive layout и reduced motion. Анимация помогает следить за результатом, не закрывает управление.

Интерактивность проверять реальными кликами и API на основном сценарии. Не выдумывать недоступные backend-возможности и численную неопределённость. Сначала полностью соединённый путь; дополнительные взаимодействия timebox20мин каждое, при риске убрать улучшение, сохранив работающий экран.
