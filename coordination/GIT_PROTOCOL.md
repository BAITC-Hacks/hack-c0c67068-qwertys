# Git как канал координации

## Ветки

- `coord/hackalem-start`: общая интеграционная ветка; только C3/уполномоченный интегратор её обновляет.
- `agent/c1-data`, `agent/c2-ml`, `agent/c4-support`, `agent/claude-review`: отдельные ветки исполнителей. Claude сохраняет имя review, но теперь также владеет frontend. C3 работает в координационной ветке. Ранее созданные ветки не переименовывать молча: сообщить фактическое имя интегратору.
- `dev1`: существующая исследовательская ветка. Сохранена и включена в исходную историю; не переименовывать и не force-push.
- `main`: ветка сдачи. Перед финальной отправкой C3 переносит проверенную интеграционную версию с соблюдением правил репозитория. Стартовый коммит сам по себе main не обновляет.

До появления удалённой ветки исполнителя выбрать соответствующую новую локальную ветку от `origin/coord/hackalem-start`. Если роль/ветка уже существует, сначала выяснить владельца, а не создавать конкурирующую копию.

## Подключение на другом ноутбуке

Команды выполняются последовательно. Пример для Claude в НОВОЙ отдельной папке; имя каталога можно изменить. При существующем checkout нельзя клонировать поверх него.

```powershell
git clone --branch coord/hackalem-start https://github.com/BAITC-Hacks/hack-c0c67068-qwertys.git hackalem-claude
cd hackalem-claude
git fetch origin
git switch -c agent/claude-review
```

Перед последней командой проверить `git branch -a`: если `origin/agent/claude-review` уже есть и принадлежит этому исполнителю, подключить её через `git switch --track origin/agent/claude-review`. Если владелец другой — остановить захват роли и написать C3.

На первом ноутбуке C3 создаёт отдельные worktrees до передачи задания. Ни один агент не делает `git switch` в папке другого агента. Незакоммиченные изменения не переносятся автоматически между рабочими копиями.

## Статусы и сообщения

Каждый владеет только `coordination/status/<ROLE>.md`. Не создавать общий файл, который все постоянно переписывают.

Новое сообщение: `coordination/messages/YYYYMMDDTHHMMSS+0500-ROLE-TYPE-short-id.md`. TYPE: `CLAIM`, `ACK`, `BLOCKER`, `REQUEST`, `READY`, `DECISION`. Имя уникально; опубликованное сообщение неизменно. Исправление — новым сообщением со ссылкой на старое.

Обязательные поля сообщения: from, to, type, local_time, task_id, branch, commit/result, requested_action, deadline, evidence, limitations. Для READY указать точный commit с кодом и команду проверки. Не ссылаться на несуществующий собственный hash ещё не созданного коммита.

В каждой рабочей ветке публикуются собственные статусы, сообщения, исследование и код. Они становятся видимыми другим через fetch, даже до merge. Просто изменение локального файла сообщением не считается.

## Цикл связи каждые10мин или при блокере

1. Сохранить собственный результат, проверить `git status` и diff; добавить только свои файлы по явным путям.
2. Сделать короткий commit с ролью/задачей и отправить в свою ветку. Первое отправление: `git push -u origin agent/<имя>`.
3. `git fetch origin` — прочитать новые сообщения и статусы из веток коллег. Не делать автоматический pull с перезаписью своей работы.
4. Интегратор читает, например, `git show origin/agent/c1-data:coordination/status/C1.md`. Список сообщений можно получить через `git ls-tree -r --name-only origin/agent/c1-data coordination/messages`.
5. Получатель публикует ACK в своей ветке со ссылкой на ID сообщения и конкретным действием. C3 отвечает в координационной ветке.
6. Перед началом следующего блока обновить свою ветку из `origin/coord/hackalem-start` обычным merge при чистом рабочем дереве. При конфликте общих файлов обратиться к C3, не выбирать ours/theirs вслепую.

Это рабочая дисциплина агентов и людей, а не установленный фоновый Git-бот. Автоматический монитор здесь не создан. BLOCKER с ближайшим сроком дополнительно сообщается человеку сразу.

## Интеграция

Только READY+проверка даёт основание принять изменения. C3 проверяет diff, команды и зависимости; объединяет небольшими порциями. Не делать одновременно merge и cherry-pick одинаковых коммитов. После принятия публикует ACK с интеграционным hash. Автор сверяет ACK и продолжает от обновлённой базы.

Если push отклонён, сделать fetch, проверить новые commits, согласовать владельца и обычное объединение. Не force-push. Для защиты данных не выполнять `git add .`: использовать явный список файлов и проверять staged diff.

Проверенная версия для сдачи фиксируется commit/tag интегратором. Сдаваемые результаты и README должны соответствовать тому же commit. Сохранённая локально, но не отправленная версия не считается переданной.
