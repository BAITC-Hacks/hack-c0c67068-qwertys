# Финальная заметка C1 для жюри: происхождение архивной погоды

Проверено 23.09.2026 по первичным источникам; новых датасетов, обучения и изменений production-порога не было.

## Что подтверждено

- [Open-Meteo Single Runs API](https://open-meteo.com/en/docs/single-runs-api) хранит отдельные прогнозные выпуски ECMWF IFS и возвращает их полный горизонт. Параметр run — **время инициализации**, а не фактического появления результата в API. Документация прямо различает эти моменты. Наши manifest фиксируют run, issue, valid, URL, SHA ответа, покрытие и статус проверки значений.
- [ECMWF](https://www.ecmwf.int/en/forecasts/documentation-and-support/changes-ecmwf-model) указывает, что цикл IFS 49r1 внедрён 12.11.2024; февраль 2026 относится к его операционному периоду. Это подтверждает эпоху модели, но **не** дату и час публикации каждого конкретного архивного ответа Open-Meteo.
- [Open-Meteo Model Updates](https://open-meteo.com/en/docs/model-updates) описывает last_run_availability_time для **последнего текущего** прогона и предупреждает о различиях между API-серверами. В нашей проверке текущего IFS от 23.09.2026 лаг составил 7 ч 00 мин 22 с. Это наблюдение опровергло первоначальные +6 ч, но ничего не доказывает о каждом прогоне 2025–2026 годов.
- В сохранённом raw ответе выпуска 2026-01-31 00Z (SHA256 3c846b4f520d1ee3f1cefa0d4be765c7cd12a41a077d026e18d083867871237e) нет поля исторического времени публикации; [открытый вопрос в репозитории Open-Meteo](https://github.com/open-meteo/open-meteo/issues/1889) спрашивает именно о таком timestamp. Проверенные документы не дают per-run журнала доступности для нашего исторического периода.

## Ограничение, которое следует показывать

Мы применяем available_at = run_init + 9 часов как **заранее зафиксированное допущение с запасом**, и проверяем available_at ≤ issue_time < valid_time. Поле availability_basis = inferred_run_plus_9h, provenance_status = unconfirmed. Эти строки являются архивными выходами отдельных модельных выпусков, но точное историческое время их публикации не подтверждено. Поэтому мы **не заявляем строго доказанное отсутствие временной утечки** для weather replay. Временную метку +9 ч нельзя называть фактическим временем публикации.

Краткая формулировка для жюри:

> Мы воспроизводим последовательные выпуски прогноза по архиву отдельных прогонов ECMWF IFS и сохраняем источник, время инициализации, целевые часы и SHA каждого ответа. Для отбора погоды на момент выпуска используем фиксированный запас 9 часов после инициализации. Поставщик не предоставляет нам историческую метку публикации каждого прогона, поэтому этот запас помечен как допущение, а историческое отсутствие утечки — неподтверждённым. После хакатона его можно проверить по журналу публикации поставщика или утверждённому организатором расписанию и повторить тот же replay без переобучения на тесте.

Строгая следующая проверка: получить per-run журнал публикации Open-Meteo/ECMWF либо официальный допуск и расписание от организатора; для каждого issue выбрать только прогоны с доказанным published_at ≤ issue и повторить зафиксированный backtest. Новую произвольную задержку вместо подтверждения не вводить.

## Проверка CLI и 12Z

В общем README команда batch_archive с 2026-01-31..02-28 вызывает код, где run_rule = daily 00Z, issue_rule = same date 12Z. Однодневный эквивалент, выполненный локально на существующем кэше **без нового HTTP-запроса**:

```powershell
python -m src.weather.batch_archive --start-date 2026-01-31 --end-date 2026-01-31 --sleep-seconds 1
```

Наблюдалось: requested=1, ready=1, failed=0. Manifest для 2026-01-31 содержит run_time=00:00Z, issue_time=12:00Z, assumed available_at=09:00Z, 48 valid часов 13:00Z 31.01 — 12:00Z 02.02. Таким образом сценарий README с 17:00 UTC+5 (=12:00Z) согласован с CLI. Чистая повторная загрузка из сети этой локальной проверкой не утверждается: здесь сработал уже проверенный кэш.
