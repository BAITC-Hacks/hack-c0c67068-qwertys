# C1 R03: можно ли доказать историческую доступность выпуска NWP?

Проверено 23.09.2026 после V1/V2 handoff, без новых архивных загрузок. Требование кейса: в последовательном прогнозировании использовать погодные входы, доступные на момент выпуска. Для строгого утверждения «без временной утечки» нужен источник исторического времени публикации **каждого** выбранного NWP-прогона либо утверждённый организатором протокол доступности.

## Что подтверждено

1. [Open-Meteo Single Runs API](https://open-meteo.com/en/docs/single-runs-api) идентифицирует прогон параметром run по **времени инициализации**, не по времени фактической публикации. Документация предупреждает о задержке вычисления и распространения после инициализации. Архив 2026-01-31/02-15/02-28 и расширенный V2 реально возвращали почасовые поля; каждый сохранённый ответ имеет URL, SHA256, покрытие и проверку числовых значений в manifests.
2. [Model Updates / Metadata API](https://open-meteo.com/en/docs/model-updates) различает last_run_initialisation_time и last_run_availability_time, но показывает **последний текущий** выпуск. В проверенном ответе 23.09.2026 текущий ECMWF IFS 00Z стал доступен в 07:00:22Z, то есть спустя 7 ч 00 мин 22 с. Поэтому исходное допущение +6 ч было опровергнуто; код использует +9 ч как запас и метки availability_basis=inferred_run_plus_9h, provenance_status=unconfirmed.
3. Локальный raw ответ Single Runs за 2026-01-31 00Z содержит ключи elevation, generationtime_ms, hourly, hourly_units, latitude, longitude, timezone, timezone_abbreviation, utc_offset_seconds; **поля исторического publication/availability timestamp нет**. Его SHA256: 3c846b4f520d1ee3f1cefa0d4be765c7cd12a41a077d026e18d083867871237e. Открытый [запрос к поставщику о таком поле](https://github.com/open-meteo/open-meteo/issues/1889) подтверждает саму нерешённую потребность.
4. [ECMWF model changes](https://www.ecmwf.int/en/forecasts/documentation-and-support/changes-ecmwf-model) относят февраль 2026 к периоду операционного IFS Cycle 49r1; это подтверждает эпоху модели, **но не час публикации конкретного Open-Meteo ответа**. 2024-11-01..11 в V2 помечены как pre-operational 49r1 hindcasts и исключаются C2 из основного fit.

## Вывод для команды

Текущие 120 V1 и 360 успешных V2 выпусков проходят проверку структуры, SHA, чисел, покрытия и допущения run+9h ≤ issue12Z. **Строгое историческое as-issued происхождение и отсутствие временной утечки пока не доказаны.** Описывать replay как conditional/assumption-based; не выдавать +9 ч за фактическую публикацию. UTC+6 для SCADA отдельно остаётся inferred: корреляция Nov–Dec поддерживает гипотезу, но не подтверждает метаданные датчика. Февральского факта выработки в выдаче нет.

## Один вопрос ментору / организатору

> Допускается ли для последовательного прогноза февраля 2026 архив Open-Meteo Single Runs ECMWF IFS HRES как источник исторически доступной погоды, если мы фиксируем время инициализации run, принимаем консервативное допущение доступности run+9 часов и честно помечаем его неподтверждённым, поскольку API не хранит per-run время публикации? Если нет, какой конкретный архив и правило исторической доступности вы считаете допустимыми для оценки кейса?

До ответа ментора не менять модельные результаты V1/V2 и не вводить новый неподтверждённый timestamp. Ответ от ментора пока не получен.
